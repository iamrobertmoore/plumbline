Your repo says it is done. Let us check.

Plumbline reads everything a project says about itself, then tests whether any of it is true. It does not tell you whether your code works. It tells you every place your project says something that is not true, ordered by what a reader would hit first.

61 of the same 100 carry commits that name an AI agent as a co-author, and 11% of their 9,936 most recent commits declare one. Measured, not cited, and deliberately a lower bound: a commit that was agent-assisted without saying so is counted as human. The method is in who wrote this code.

The first pass of this measurement said 89 of 100. That was wrong, and it was wrong in the direction that flattered the tool, so I went back through the findings by hand until the number survived scrutiny. Seven corrections are written up in the method. The figure moved 89 to 47 to 30 to 22 to 19 to 18, and every move was downward.

02 · A real finding

One README. One document. Two filenames.

From ruvnet/RuView, rank 90 of the 100, and one of the 18 that fail. Its README links the same architecture decision record twice, to two different files. 

[ADR-079](docs/adr/ADR-079-camera-ground-truth-training.md)      exists
[ADR-079](docs/adr/ADR-079-camera-supervised-pose-finetune.md)   never existed

A reader clicks that and gets a 404. The author never saw it, because they never clicked their own link after renaming the file. No test catches this. Nothing in CI reads the README.

03 · Why this is not a bundle of linters

Every check proves it can fail.

Link checkers exist. Drift detectors exist, and they only see what a commit touched, so a README that was wrong when it was written stays invisible. What none of them do is prove their own checks can fail. Before Plumbline is allowed to report a pass, it runs that check against an input built to fail it. A check that does not fail is reported as unproven, never as a pass. Every row below names the check, what it asserts, and the input it is broken with.

provenlink.relative   relative links point at files that existbroken on purpose: __plumbline_missing__/README.md, linked but not present → reports it missing
provenlink.external   external links resolvebroken on purpose: https://plumbline.invalid/__control__, a host that does not answer → reports ERR
proveninstall   the install command names a package that existsbroken on purpose: npm install plumbline-control-package-that-does-not-exist → reports no such package
provenmanifest.version   the manifest version is publishedbroken on purpose: manifest says 0.0.0-plumbline-control, registry says 1.3.0 → reports the disagreement
provenlicense.claimed   the licence is detectablebroken on purpose: a README claiming a licence with no licence file at the root → reports it cannot detect one
provenci.claimed   CI is claimed and a workflow existsbroken on purpose: a README claiming CI with no .github/workflows directory → reports none exists

This exists because I shipped a green CI badge that was doing nothing at all: a conformance job that ran nightly for days and skipped every test, because it gated on a credential that did not exist. It passed, so nothing drew attention to it. I found it on submission day.

05 · How Bob is used

Four of Bob's capabilities do real work here.

Document understanding

Claims come out of real documents, not just markdown. Bob reads .docx, .pdf and .xlsx as they are, so a spec, a release checklist or a test plan can be the source of a claim.

Subagents

One subagent per claim, each with its own clean context, so nothing gets checked by accident while something else is being checked.

Parallel tasks

Claims that do not depend on each other are checked at the same time, so a hundred-repository corpus does not have to queue up.

Agent mode

Runs the whole thing, decides what is left to check, and writes the result. If Bob is unavailable, those claims are reported as unverified, never as passing.

The flagship check is test-plan coverage: read an .xlsx test plan as it is, trace every case to a test that exists, and list the ones nobody wrote. No existing tool can do that, because no existing tool reads the plan.

06 · Run it

Two commands.

# audit the repository in the current directory
npx github:iamrobertmoore/plumbline --repo .

# prove that every check can fail before trusting any of them
npx github:iamrobertmoore/plumbline --selfcheck

Exits 0 on pass, 1 on a failed check, 2 when a check cannot be shown to fail. Zero runtime dependencies. Reads the repository and writes nothing.

07 · Honest limitations

A failing check is not broken software.

A dead link in a README does not stop anyone installing the package. That is exactly why these defects survive: no test reads what the documentation claims.

The number is a snapshot, and it carries its date for that reason. The corpus is deliberately the strongest end of GitHub, so 18% is a floor rather than an average. Workflows that can pass without asserting anything are reported as warnings and kept out of the headline, because continue-on-error on a docs job is a deliberate choice rather than a lie.

A claim the tool cannot observe is reported as not observable, never as a pass and never as a failure. If the About panel cannot be seen, or a package name turns out to belong to a different project, Plumbline says so and moves on. It does not guess, and it does not accuse.
